Is it possible to associate UEs to different RUs and assign specific RBs to them based on “A”
computed from python code?
This depends on how the 3 RUs are defined in your OAI configuration.
Scenario A: 3 RUs = 3 Separate Cells (Natively Supported)
If each RU is broadcasting its own Cell ID (e.g., they operate on slightly different frequencies, or they reuse frequencies
but act as distinct base stations), then associating a UE to an RU is simply Cell Association/Handover.
●​ How it works: Your Python code calculates the distance and decides "UE 5 should connect to RU 2". Your
Python code sends an RRC control command (via FlexRIC) to trigger a handover for UE 5 to Cell 2. Once
connected, your Python code sends the specific RB allocation for UE 5 to Cell 2's MAC scheduler.
●​ Support Level: Highly supported. O-RAN natively handles load-balancing and handover commands via the E2
interface.

The Easy Part: Specific RB to UE Mapping
Assigning exactly 1 specific RB to a specific UE based on your Rayleigh channel calculations in Python is absolutely
possible.
●​ As mentioned before, by using FlexRIC (or a custom socket), your Python code can send a PRB allocation mask
to the gNB's MAC scheduler.
●​ You can tell the MAC: "At slot $t$, assign RB $x$ to UE $y$." The MAC scheduler will accept this and override its
internal round-robin/proportional-fair algorithm.

How to instantiate UEs with different path losses?
You do not need to write custom C code to change the distance or path loss. OAI has a built-in Telnet Server API
specifically designed to let external scripts dynamically modify the physical channel while the simulation is running.
Here is exactly how it is configured and controlled:

1. Initial Configuration (The .conf file)
When you start the OAI gNB and UEs with rfsimulator, you provide a channel model configuration file (e.g.,
channelmod_rfsimu.conf). In this file, you can define a distinct channel model for each of your 20 UEs.
For example, you define a model for UE 1 and UE 2:
text
modellist_rfsimu_1 = (
{
model_name
= "rfsimu_channel_ue1"
type
= "AWGN";
ploss_dB
= 20;
noise_power_dB = -2;
},
{
model_name
= "rfsimu_channel_ue2"
type
= "AWGN";
ploss_dB
= 40;
noise_power_dB = -2;
}
);
When UE 1 connects, it gets rfsimu_channel_ue1. When UE 2 connects, it gets rfsimu_channel_ue2.

2. Real-Time Control from Python (The Telnet API)
Once OAI is running, it opens a Telnet server on port 9090.

Your Python DRL script can open a standard socket connection to 127.0.0.1:9090 and send string commands to
dynamically change the environment on the fly.
To change the distance of a specific UE: Your Python script sends: rfsimu setdistance rfsimu_channel_ue1 500
(Sets UE 1's distance to 500 meters)
To change the raw Path Loss of a specific UE: If your Python script calculates a complex path loss that distance alone
doesn't cover, you can directly overwrite the path loss (in dB): channelmod modify 0 ploss 85.5 (Changes the path
loss of channel index 0 to 85.5 dB)

How to integrate this with your DRL script:
Since you already have Approach 1 working, extending it to OAI would look like this:
1.​ Start OAI gNB with the --telnetsrv and --rfsimulator.[0].options chanmod flags.
2.​ Start your 20 OAI UEs.
3.​ In your Python loop:
●​ Calculate the new positions/distances of your 20 UEs.
●​ Send 20 quick telnet commands to OAI's port 9090 to update setdistance or ploss for each UE's
channel model.
●​ Execute your DRL actions (e.g., RB allocations via FlexRIC).
●​ Wait for the next step.
This built-in API makes connecting your Python environment's mobility models to OAI's physical layer simulator extremely
seamless!

You can keep your entire UE placement, mobility, and abstract path loss calculations completely inside your external
Python code. You do not need to port any of that logic into OAI.
Your Python code essentially acts as a "Master Controller" that dictates the environment to OAI:
1.​ Python calculates that UE 5 moved behind a building, and its path loss is now 110.5 dB.
2.​ Python opens a socket to 127.0.0.1:9090 (OAI's Telnet Server).
3.​ Python sends: channelmod modify 4 ploss 110.5 (assuming 4 is UE 5's channel index).
4.​ OAI's rfsimulator instantly applies a 110.5 dB attenuation to all the simulated radio waves going to and from UE
5.
This completely separates your simulation logic (Python) from the heavy protocol stack operations (OAI), giving you the
exact abstraction you are looking for while still running a full 5G network under the hood.

Potential issues

Multi-cell interference - supported in USRP, but RFSIM = interference is not taken into account by
design
OAI absolutely has the concept of Inter-Cell Interference (ICI) in its math and protocol stack. The limitation is
purely in the "plumbing" of the software simulator (rfsimulator).
Let me explain the difference between running OAI in the real world versus in the software simulator:

1. In the Real World (Using USRP Radios)
If you deploy your 3 OAI gNBs using actual radio hardware (like USRPs) and real antennas, interference works exactly
as you would expect.
●​ The air acts as the mixing medium.
●​ The UE's physical antenna picks up the strong signal from RU 1, and the weaker interfering electromagnetic
waves from RU 2 and RU 3.
●​ OAI’s Physical Layer algorithms (the C code) will process that messy waveform, calculate the true SINR,
experience decoding errors due to the interference, and request HARQ retransmissions.

2. In Software Simulation (rfsimulator)
When you don't use real radios, rfsimulator replaces the antennas with a TCP/IP socket. This is where the problem
lies.
●​ In the real world, an antenna passively hears everything around it.
●​ In software, a TCP socket is a strict, point-to-point pipeline.
●​ Your simulated UE opens a socket to connect to its serving gNB. Because it is only "plugged in" to that
one gNB's IP address, the IQ samples (the simulated radio waves) from the other two gNBs physically
cannot enter the UE's process.
●​ Since the UE's software never receives the data from the other cells, it experiences a perfectly clean,
interference-free channel.

Work around - use custom python scripts
Does OAI support PA distortion modeling?
No, OAI does not natively model non-linear PA distortion out of the box. The software simulator assumes the base
station has a perfect, ideal, linear transmitter.
However, you can absolutely do it, and this is exactly why the Custom Python Emulator we discussed earlier is
the perfect architecture for your research.
Since you already have the math for the Bussgang approximation working in Python, here is how you implement your
entire physical model (Distortion + Path Loss + ICI) without touching a single line of OAI's C-code:

The Data Flow with PA Distortion
1.​ The Perfect Signal: Your 3 OAI gNBs generate their standard, perfect digital OFDM waveforms (I/Q samples)
and send them out over their TCP sockets.
2.​ Apply PA Distortion in Python: Your Python proxy script receives these 3 perfect waveforms. Because you
have the raw time-domain IQ samples, you simply run them through your Bussgang PA distortion function in
Python. Now you have the realistic, distorted waveforms for each RU.
3.​ Apply Path Loss: You multiply those distorted waveforms by your path loss scalars based on the UE's distance.
4.​ Mix for Interference (ICI): Because all your RUs share the same RBs, you just mathematically add the 3
distorted, attenuated waveforms together into one signal.
5.​ The Realistic Reception: You send that final, messy waveform to the OAI UE.
